# Methodology

Основная цель MVP - не найти универсально лучший индекс, а на одном
воспроизводимом предметном срезе OpenAlex сравнить поведение индексов,
устойчивость рангов и ограничения данных. Для этого в системе оставлен один
исследовательский контур:

- сначала загружается предметный срез `/works` как фиксированный компактный
  JSONL-дамп;
- затем `authorships` нормализуется в локальные таблицы;
- после этого авторские индексы считаются только по работам внутри выбранного
  среза.

OpenAlex Author object и глобальные `summary_stats` не используются как
источник итоговых рейтингов. Точечное обращение к OpenAlex остается только для
разрешения сущностей и справочных карточек, если оно явно зафиксировано в
паспорте расчета.

## Срез

Срез по умолчанию:

- endpoint: `https://api.openalex.org/works`
- предметный фильтр: `primary_topic.subfield.id:2604`
- название: `Applied Mathematics`
- период: `2020-01-01` - `2024-12-31`
- тип работы: `article`; расширенный режим допускает
  `article|review|conference-paper`
- исключения: `is_retracted:false`, `is_paratext:false`, `is_xpac:false`
- keyword: опциональный фильтр `keywords.id` после выбора OpenAlex keyword
- организация: опциональный фильтр `authorships.institutions.id`
- страна автора: опциональный фильтр по `authorships.institutions.country_code`
- сортировка: `publication_date:asc,openalex:asc`

UI не показывает фильтры пола и возраста, потому что OpenAlex не предоставляет
эти поля для работ или авторств. Город не является штатным OpenAlex-фильтром
для Authors/Institutions; его можно добавлять позже через внешний справочник
организаций города и преобразование в institution IDs.

## Метрики

Ядро MVP рассчитывается по авторам внутри текущего среза:

- `P`: число работ автора;
- `C`: сумма `cited_by_count`;
- `C_frac`: сумма цитирований с учетом доли автора;
- `CPP`: средняя цитируемость одной работы `C / P`;
- `h`: индекс Хирша;
- `i10`: число работ с 10+ цитированиями;
- `g`: g-index;
- `m_local`: локальный темп `h / возраст_публикационного_окна_автора`.

Интегральный показатель и диагностические расширения считаются отдельно и не
подменяют ядро сравнения:

- `LRDI`: локальный робастный дробно-взвешенный индекс
  `P/(P+p0) * sum(log(1+c_i) / m_i * exp(-lambda * age_i))`;
- `f5`: операционное число работ автора с `cited_by_count >= 5`;
- `fm5`: операционная сумма авторских долей для работ с
  `cited_by_count >= 5`;
- `IUPV`: индекс устойчивой предметной видимости
  `100 * (pr(P) * pr(h) * pr(C_frac)) ** (1/3)`, где `pr(.)` -
  процентильный ранг внутри текущего среза и режима фракционирования.
- `ISLV`: индекс сбалансированного локального вклада
  `100 * G * K_conc`, где `G` - взвешенное геометрическое среднее
  процентилей `h`, `C_frac`, `g`, `i10`, `P`, а `K_conc` снижает оценку при
  чрезмерной доле самой цитируемой работы.

В интерфейсе `ISLV` выбран как стартовый рейтинг, потому что он объединяет
устойчивое citation-core, фракционную цитируемость, g-index, i10 и слабый
сигнал продуктивности, но дополнительно показывает чувствительность к одной
сверхцитируемой работе. В методическом выводе он должен сравниваться рядом с
`P`, `C`, `C_frac`, `CPP`, `h`, `i10`, `g` и `m_local`, а не использоваться как
единственное основание решения.

Метрики и их назначение вынесены в `configs/metric_registry.yaml`. В этом
реестре локальные показатели имеют источник `computed_from_slice_works`.
Глобальные поля OpenAlex Authors (`works_count`, `cited_by_count`,
`summary_stats.h_index`, `summary_stats.i10_index`,
`summary_stats.2yr_mean_citedness`) описаны отдельно как
`openalex_author_object` и используются только в быстрой витрине.

`f5/fm5` в этом MVP специально помечены как operational definition. Перед
использованием в тексте диплома как индексов Полянина нужно подтвердить
каноническое определение первоисточником.

Поддерживаются три режима учета:

- `strict_authors_count`: вклад делится на наблюдаемое число authorships;
- `renorm_valid_authors`: вклад делится только между валидными авторами;
- `integer`: каждая работа засчитывается автору целиком.

OpenAlex Works API возвращает вложенные `authorships`; MVP нормализует их
локально, использует наблюдаемый размер authorships как знаменатель и фиксирует
ограничения в `quality_report`.

## Ранжирование

Одинаковое правило ранжирования используется в `rating_positions.csv`,
интерактивном API и UI:

1. выбранный индекс по убыванию;
2. `C` по убыванию;
3. `P` по убыванию;
4. `author_id` по возрастанию.

Это правило зафиксировано в `configs/ranking_profiles.yaml` и записывается в
`calculation_passport.json`. За счет этого экспортированный CSV и экранная
таблица не расходятся при равных значениях основного индекса.

## Data Flow

1. Пользователь выбирает область, подобласть или тему OpenAlex по названию.
2. Пользователь задает период, страну автора и объем загрузки.
3. Пользователь при необходимости выбирает keyword и организацию через
   подсказки OpenAlex.
4. Backend показывает точный OpenAlex filter, search и select.
5. Backend скачивает фиксированный Works JSONL-dump или импортирует уже
   существующий локальный OpenAlex Works dump.
6. JSON нормализуется в тонкий curated-слой `works_flat` и
   `authorships_flat`; dependency-light реализация пишет CSV, production-слой
   зарезервирован под slice-based Parquet.
7. Собирается mart `author_work_metrics.csv`.
8. Считаются `author_indices.csv`, `rating_positions.csv`, статистика и
   паспорта воспроизводимости.
9. UI обновляет рейтинг, ящик с усами, линейное сравнение индексов, плоские
   таблицы и CSV/JSON export.

## Минимальный аналитический протокол

Обязательный пакет результатов для математического вывода:

- descriptive statistics по `P`, `C`, `C_frac`, `CPP`, `h`, `i10`, `g`,
  `m_local`;
- Spearman и Kendall tau-b для рангов;
- overlap@10/20/50 между индексами;
- leave-top1 sensitivity и сдвиг рангов;
- сравнение `C` vs `C_frac` как проверка эффекта соавторства;
- quality funnel: сырые работы, плоские авторства, NULL/deleted authors,
  авторы с локальными индексами.

`report_bundle.json` объединяет паспорт среза, quality report, ranking table,
statistics, stability report и ссылки на CSV exports.

## Воспроизводимые слои хранения

Целевой контур хранения для развития СППР размещается вне репозитория, в
каталоге `OPENALEX_DSS_DATA_DIR`:

- `$OPENALEX_DSS_DATA_DIR/raw/{slice_id}/` - неизменяемые API pages / локальный микродамп;
- `data/ref/` и `config/mappings/vak_topic_mapping.yaml` - mapping ВАК ->
  OpenAlex topics/subfields/keywords;
- `$OPENALEX_DSS_DATA_DIR/curated/{slice_id}/` - тонкие `works_flat` и `authorships_flat`;
- `$OPENALEX_DSS_DATA_DIR/marts/{slice_id}/` - `author_work_metrics` и `author_indices`;
- `$OPENALEX_DSS_DATA_DIR/reports/{slice_id}/` - CSV/JSON/графики отчета;
- `$OPENALEX_DSS_DATA_DIR/passports/` - паспорта текущего запуска;
- `$OPENALEX_DSS_DATA_DIR/checksums/{slice_id}/sha256_manifest.txt` - контрольные суммы.

Текущая реализация сохраняет latest-view CSV и Parquet-файлы в
`data/normalized`, `data/parquet`, `data/marts`, `data/results`; в приложении
эти пути являются виртуальным алиасом на внешний `OPENALEX_DSS_DATA_DIR`, а не
папкой внутри репозитория.

## Компактный дамп MVP

Для ноутбука и воспроизводимой проверки используется не полный OpenAlex S3
snapshot, а компактный API-срез:

```bash
python3 scripts/01_fetch_openalex_slice.py \
  --config config/slice.yaml \
  --out-dir data/raw/openalex_slices/{slice_id} \
  --max-records 50000 \
  --max-bytes 524288000
```

Скрипт создает:

- `works.jsonl` - неизменяемый raw-файл работ выбранного среза;
- `slice_passport.json` - фильтр OpenAlex, `select`, лимиты, число записей,
  причину остановки, SHA-256 и заметку, что это compact slice, а не полный
  snapshot.

Если путь начинается с `data/`, CLI и backend сохраняют файл во внешний
`OPENALEX_DSS_DATA_DIR`, поэтому тяжелые дампы и таблицы не попадают в
репозиторий.

После этого нормализация и расчет индексов должны выполняться локально от
зафиксированного JSONL. API используется только для первичного скачивания
фиксированного среза, подсказок/ID в выпадающих списках и точечного
дообогащения авторов или публикаций.

В UI этот же режим находится в рабочей области `Выборка`: пользователь
выбирает предметный срез, страну, организацию, период и типы работ. Система
оценивает число работ, API-страниц и размер raw/parquet до загрузки; после
подтверждения выполняется единое действие `Скачать срез`, которое сохраняет
JSONL и запускает локальную нормализацию без повторного обращения к OpenAlex.
Для сервера скачивание остается отдельным endpoint
`/api/v1/pipeline/fetch-slice-dump`; он не смешивает raw dump с витринами.
