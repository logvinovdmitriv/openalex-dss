# Methodology

Основная цель DSS - не найти универсально лучший индекс, а на одном
воспроизводимом предметном срезе OpenAlex сравнить поведение индексов,
устойчивость рангов и ограничения данных. Для этого в системе оставлен один
исследовательский контур:

- сначала предметный срез работ OpenAlex материализуется выбранным backend
  provider как фиксированный компактный JSONL.GZ-дамп;
- затем `authorships` нормализуется в локальные таблицы;
- после этого авторские индексы считаются только по работам внутри выбранного
  среза.

OpenAlex Author object и глобальные `summary_stats` не используются как
источник итоговых рейтингов. Точечное обращение к OpenAlex остается только для
разрешения сущностей и справочных карточек, если оно явно зафиксировано в
паспорте расчета.

## Срез

Срез по умолчанию:

- источник оценки: `https://api.openalex.org/works`
- источник скачивания: backend download provider, выбранный планом
  материализации; по умолчанию OpenAlex CLI для совместимых works-фильтров,
  API cursor или ids hydration для API-сценариев, локальный snapshot scan для
  уже доступных snapshot partitions
- предметный фильтр: `primary_topic.subfield.id:2604`
- название: `Applied Mathematics`
- период: `2020-01-01` - `2024-12-31`
- тип работы: `article`; расширенный режим допускает
  `article|review`; конференционные источники задаются через source type `conference`,
  а не через отдельный work type
- исключения: `is_retracted:false`, `is_paratext:false`, `is_xpac:false`
- keyword: опциональный фильтр `keywords.id` после выбора OpenAlex keyword
- организация: опциональный фильтр `authorships.institutions.id`
- страна автора: опциональный фильтр по `authorships.institutions.country_code`
- сортировка: `publication_date:asc,openalex:asc`

Фильтры уровня `authorships` (автор, организация автора, страна организации
автора) считаются рисковыми для первичной OpenAlex pushdown-загрузки: в
списковых ответах OpenAlex вложенный список авторств может быть обрезан у
гиперавторских работ. Поэтому для финального отчета такие ограничения должны
применяться на локальном mart-слое после материализации полного work-level
среза. Pushdown по этим фильтрам допускается только как быстрый предварительный
режим оценки/чернового просмотра и маркируется в системе как
`fetch_pushdown_risky_authorship`.

В интерфейсе и API дополнительно различаются две семантики локальных
ограничений по стране/организации. `author_cohort_filter` выбирает авторов,
у которых в полном срезе есть хотя бы одно авторство с указанной страной или
организацией; уже рассчитанные индексы такого автора при этом не
пересчитываются по подмножеству работ. `work_scope_filter` означает новый
аналитический срез: сначала локально отбираются работы/авторства, затем заново
строятся `author_work`, `indices` и `ratings`. Финальные выводы о рейтингах
по стране или организации должны указывать, какая из этих семантик
использована.

Каталог фильтров отдается backend-ом через `/api/v1/openalex/filter-catalog`.
Каждая запись содержит техническое поле OpenAlex, русское название,
тип UI-контрола, источник справочных значений, совместимость со способом
скачивания, риск для финального анализа и локальный эквивалент. Русские
подписи и подсказки вынесены в `configs/i18n/openalex_filters.ru.yaml`, чтобы
UI не хранил научную терминологию и правила совместимости в React-коде.

UI не показывает фильтры пола и возраста, потому что OpenAlex не предоставляет
эти поля для работ или авторств. Город не является штатным OpenAlex-фильтром
для Authors/Institutions; его можно добавлять позже через внешний справочник
организаций города и преобразование в institution IDs.

## Метрики

Ядро DSS рассчитывается по авторам внутри текущего среза:

- публикации: число работ автора;
- цитирования: сумма `cited_by_count`;
- цитирования с долевым учетом: сумма цитирований с учетом доли автора;
- индекс Хирша;
- i10-индекс: число работ с 10+ цитированиями;
- g-индекс.

Средняя цитируемость, m-индекс внутри среза, интегральные формулы и
диагностические расширения считаются отдельно и не
подменяют ядро сравнения:

- средняя цитируемость: цитирования / публикации;
- m-индекс внутри среза: индекс Хирша / возраст публикационного окна автора;
- робастный локальный индекс
  `P/(P+p0) * sum(log(1+c_i) / m_i * exp(-lambda * age_i))`;
- публикации с 5+ цитированиями: операционное число работ автора с `cited_by_count >= 5`;
- долевой вклад публикаций с 5+ цитированиями: операционная сумма авторских долей для работ с
  `cited_by_count >= 5`;
- процентильная формула активности и цитируемости
  `100 * (pr(P) * pr(h) * pr(C_frac)) ** (1/3)`, где `pr(.)` -
  процентильный ранг внутри текущего среза и выбранного способа учета вклада авторов.
- процентильная формула сбалансированного вклада
  `100 * G * K_conc`, где `G` - взвешенное геометрическое среднее
  процентилей `h`, `C_frac`, `g`, `i10`, `P`, а `K_conc` снижает оценку при
  чрезмерной доле самой цитируемой работы.

В интерфейсе по умолчанию используются общеупотребимые показатели ядра:
публикации, цитирования, долевые цитирования, индекс Хирша, i10-индекс и
g-индекс. Дополнительные исследовательские формулы доступны в аналитическом
слое, но не подменяют основные показатели и не используются как единственное
основание решения.

Метрики и их назначение вынесены в `configs/metric_registry.yaml`. В этом
реестре локальные показатели имеют источник `computed_from_slice_works`.
Глобальные поля OpenAlex Authors (`works_count`, `cited_by_count`,
`summary_stats.h_index`, `summary_stats.i10_index`,
`summary_stats.2yr_mean_citedness`) описаны отдельно как
`openalex_author_object` и используются только в быстрой витрине.

Пороговые показатели `n_cited5/frac_cited5` в этом DSS являются операционными
диагностическими показателями: число работ с 5+ цитированиями и долевой вклад в
такие работы.
Они не подаются как канонические именованные индексы без отдельного подтверждения
первоисточником и вынесены из базового набора популярных показателей.

Новые отчеты и формулы используют явные идентификаторы `pci`, `iupv_s` и
`iupv_sb`. Старый неявный алиас для `PCI` удален из новых выходных таблиц и
не принимается как поле для пользовательских формул.

### IUPV-S: робастный долевой вклад

`IUPV-S` является дополнительной авторской формулой, а не заменой базовых
популярных индексов. Формула использует только данные текущего локального
среза и выбранного режима учета вклада авторов.

Для каждой строки `author_work`:

```text
cited_credit_i = cited_by_count_i * credit_weight_i
r_i = log1p(cited_credit_i)
```

Для автора:

```text
RFI(a) = Σ r_i
```

Итоговая шкала:

```text
IUPV-S(a) = 0, если RFI(a) = 0
IUPV-S(a) = 100 * percentile_rank(RFI(a)), если RFI(a) > 0
```

Процентиль считается внутри одного `run_id`, одного `fraction_mode` и текущей
backend-выборки. Для неотрицательных наукометрических показателей действует
единое правило: нулевые значения получают процентиль `0`, положительные
значения ранжируются внутри множества положительных значений; совпадающие
значения получают одинаковый average-rank percentile. Это же правило применяется
в `metrics.py`, Python-вычислении пользовательских формул и DuckDB-вычислении
`pr_*`.

Смысл формулы:

- `cited_credit` учитывает долевой вклад автора в работу;
- `log1p` снижает чрезмерное влияние единичных citation outliers;
- сумма по всем работам не использует жесткий top-N порог;
- шкала `0-100` показывает место автора внутри выбранного среза, а не
  глобальную оценку ученого.

Поддерживаются три режима учета:

- `strict_authors_count`: вклад делится на reported `authors_count`, если он
  есть в OpenAlex, иначе на наблюдаемое число authorships;
- `renorm_valid_authors`: вклад делится только между валидными авторами;
- `integer`: каждая работа засчитывается автору целиком.

OpenAlex Works API возвращает вложенные `authorships`; DSS нормализует их
локально, отдельно хранит знаменатель начисления вклада и фактическое число
авторов для диагностик. Поэтому integer-режим не превращает многоавторские
работы в одноавторские при расчете `mean_authors_per_work` и
`share_single_authored`.

## Ранжирование

Одинаковое правило ранжирования используется в `ratings.csv`,
интерактивном API и UI:

1. выбранный индекс по убыванию;
2. `C` по убыванию;
3. `P` по убыванию;
4. `author_id` по возрастанию.

Это правило зафиксировано в `configs/ranking_profiles.yaml` и записывается в
`calculation_passport.json`. Поле `position` фиксирует уникальную позицию после
tie-breakers. Поле `rank_ordinal` является тем же уникальным порядком для
экспорта и последующего сравнения мест. Поля `rank_competition` и `rank_dense`
сохраняют стандартные статистические ранги по самому значению показателя.

## Протокол анализа

Базовый протокол сравнения описан в `configs/analysis_protocols.yaml`. Он
фиксирует:

- ядро показателей: `P`, `C`, `C_frac`, `h`, `i10`, `g`;
- диагностические показатели: средняя цитируемость, доля самой цитируемой
  работы, среднее число авторов и флаги качества;
- экспериментальные формулы: пороговые показатели, процентильные формулы и
  робастный локальный индекс;
- пары для сравнения рангов: `C` против `C_frac`, `h` против `g`, `h` против
  `i10`, `P` против `h`;
- размеры top-N overlap: 10, 20, 50, 100.

В аналитическом JSON дополнительно формируются табличные блоки:

- `metric_rank_summary`: одна строка на показатель с нулевой долей, tie-rate,
  квартилями, p90/p95/p99 и концентрацией верхних 10/20 значений;
- `pairwise_metric_comparison`: одна строка на пару показателей со Spearman,
  Kendall tau-b, Pearson по `log1p` и top-N overlap;
- `top_overlap`: матрица overlap с нормировкой
  `|Top_N(A) ∩ Top_N(B)| / min(N, available_authors_A, available_authors_B)`.

Все сравнения выполняются на общем множестве авторов, для которых определены
обе сравниваемые метрики. Это предотвращает сравнение рангов, построенных на
разных выборках.

## Data Flow

1. Пользователь выбирает область, подобласть или тему OpenAlex по названию.
2. Пользователь задает период, страну автора и организацию; объем загрузки
   система прогнозирует автоматически.
3. Пользователь при необходимости выбирает keyword и организацию через
   подсказки OpenAlex.
4. Backend показывает точный OpenAlex filter, search, оценку объема, стоимость
   оценки и доступные лимиты API.
   Оценка объема разделяется на selected API payload, полный metadata JSONL,
   пик временных файлов загрузчика, итоговый `works.jsonl.gz`, parquet-таблицы
   и рекомендуемое свободное место на диске.
5. Backend запускает выбранный provider: OpenAlex CLI, API cursor,
   ids hydration, локальный snapshot scan или импорт уже существующего
   локального файла OpenAlex Works.
6. JSON нормализуется во временный scoped staging
   `dumps/{dump_id}/normalized` и `dumps/{dump_id}/parquet`, после чего
   canonical таблицы корпуса материализуются в `tables/{dump_id}`, а staging
   удаляется.
7. Собирается расчетная таблица `author_work.csv`. На этом mart-слое повторно
   применяются защитные фильтры по `type`, периоду публикации, `is_retracted`,
   `is_paratext` и `is_xpac`, даже если они уже были в запросе загрузчика.
8. Считаются `indices.csv`, `ratings.csv`, их parquet-пары и паспорта
   воспроизводимости под `runs/{run_id}`.
9. Сразу после расчета строятся дефолтный report bundle и дефолтный cache
   наукометрической аналитики, чтобы при повторном открытии интерфейс читал
   готовые scoped artifacts.
10. UI обновляет рейтинг, ящик с усами, линейное сравнение индексов, плоские
    таблицы и CSV/JSON export.

## Минимальный аналитический протокол

Обязательный пакет результатов для математического вывода:

- descriptive statistics по `P`, `C`, `C_frac`, `CPP`, `h`, `i10`, `g`,
  `m_local`;
- Spearman и Kendall tau-b для рангов;
- overlap@10/20/50 между индексами;
- сдвиги рангов и совпадение первых авторов между базовым и сравниваемыми индексами;
- сравнение `C` vs `C_frac` как проверка эффекта соавторства;
- quality funnel: сырые работы, плоские авторства, NULL/deleted authors,
  авторы с локальными индексами.

`report_bundle.json` объединяет паспорт среза, quality report, ranking table,
`scientometric_analysis`, findings/conclusion exports и ссылки на CSV exports.

## Воспроизводимые слои хранения

Целевой контур хранения для развития СППР размещается вне репозитория, в
каталоге `OPENALEX_DSS_DATA_DIR`:

- `$OPENALEX_DSS_DATA_DIR/raw/openalex_cli/{slice_id}/` - неизменяемые исходные файлы локального среза;
- `data/ref/` и `config/mappings/vak_topic_mapping.yaml` - mapping ВАК ->
  OpenAlex topics/subfields/keywords;
- `$OPENALEX_DSS_DATA_DIR/dumps/{dump_id}/normalized/` - временный staging CSV на время импорта;
- `$OPENALEX_DSS_DATA_DIR/tables/{dump_id}/` - canonical parquet-таблицы локального корпуса;
- `$OPENALEX_DSS_DATA_DIR/runs/{run_id}/tables/` - производные расчетные таблицы `author_work`, `indices`, `ratings`;
- `$OPENALEX_DSS_DATA_DIR/runs/{run_id}/passports/` - паспорта и checksum manifest текущего запуска;
- `$OPENALEX_DSS_DATA_DIR/runs/{run_id}/reports/` - воспроизводимый report bundle.

Временные staging-каталоги среза удаляются после успешной материализации
canonical parquet-таблиц. Производные report/analytics artifacts ограничиваются
по числу сохраненных файлов, чтобы хранилище не разрасталось при повторных
расчетах и изменении настроек визуализации.

Приложение читает эти артефакты только через явный `dump_id`/`run_id`; глобальные
fallback-пути не используются как источник аналитики.

Перед созданием нового плана материализации backend ищет уже скачанные dumps и
показывает совместимость с текущим срезом: `exact_match`, `compatible_superset`,
`compatible_subset`, `incompatible` или `unknown`. Exact-match dump можно
переиспользовать без новой загрузки; partial или unknown dump допускается только
для предварительного просмотра, если паспорт не подтверждает финальную полноту.

## Инвариант backend-first

Все научные таблицы и графики строятся как результат backend-запроса по полному
выбранному срезу или по явно заданной backend-выборке. Frontend не имеет права
досортировывать, дофильтровывать или пересчитывать научные данные по уже
загруженной странице таблицы.

Обязательные правила:

- поиск, фильтры, сортировка, TOP-N, пагинация, рейтинги, распределения,
  корреляции, overlap и rank-delta выполняются на backend через DuckDB/Parquet
  или через заранее материализованные summary/cache-таблицы;
- frontend получает только готовую страницу строк, готовый chart payload или
  статус `not_chartable`;
- каждый аналитический payload содержит явные `analysis_id`, `filters_hash`,
  `data_scope`, `analysis_author_scope` и `final_analysis`, чтобы любое число
  можно было связать с конкретным `run_id`, `dump_id`, режимом учета и набором
  backend-фильтров;
- если график нельзя корректно интерпретировать (`no_data`, `all_zero`,
  `constant_values`, `zero_iqr`, `not_enough_rows`), UI показывает человеческое
  объяснение и не рисует пустую или ложную диаграмму;
- глобальный поиск ограничен whitelisted текстовыми полями таблицы, чтобы не
  сканировать все колонки большого среза;
- CSV exports и большие рейтинги отдаются streaming-ответом, без сборки всего
  результата в памяти frontend или backend.

## Локальный срез DSS

Для ноутбука и воспроизводимой проверки используется не полная копия OpenAlex,
а локальный срез, материализованный одним из backend providers. Для
совместимого works-filter сценария может применяться OpenAlex CLI:

```bash
openalex download \
  --api-key YOUR_KEY \
  --output data/raw/openalex_cli/{slice_id}/files \
  --filter "primary_topic.subfield.id:2604,from_publication_date:2020-01-01,to_publication_date:2024-12-31"
```

Backend упаковывает результат загрузки в:

- `works.jsonl.gz` - неизменяемый исходный файл работ выбранного среза;
- `slice_passport.json` - фильтр OpenAlex, способ загрузки, число записей,
  сигнатуры оценки и загрузки, SHA-256, версию загрузчика, журналы выполнения и
  заметку, что это локальный срез, а не полная копия OpenAlex.

Важно: OpenAlex CLI provider поддерживает `--filter`, `--ids`, `--stdin` и
`--sample`, но не поддерживает API-параметры `search`, `select` и `sort` как
часть `openalex download --filter`. Поэтому full-text `search` оценивается и
материализуется через API/IDs provider, а не маскируется под эквивалентный CLI
filter.

Если путь начинается с `data/`, загрузчик и backend сохраняют файл во внешний
`OPENALEX_DSS_DATA_DIR`, поэтому тяжелые дампы и таблицы не попадают в
репозиторий.

После этого нормализация и расчет индексов выполняются локально от
зафиксированного JSONL.GZ. API используется только для подсказок/ID в
выпадающих списках, OpenAlex field/filter справочников, оценки объема,
просмотра доступных лимитов и точечного дообогащения авторов или публикаций.

В UI этот же режим находится в рабочей области `Выборка`: пользователь
выбирает предметный срез, страну, организацию, период и типы работ. Система
оценивает число работ, стоимость estimate-запросов и размер raw/parquet до загрузки; после

`/api/v1/materializations/{materialization_id}/run`; он не смешивает raw dump с витринами.
